# 10xCards — Domain Distillation

## Step 0 — Project context

Source documents found and read in full:

- `context/foundation/prd.md` (v3, greenfield PRD — vision, personas, success criteria, FR-001..FR-010, NFRs, Business Logic, Access Control, Non-Goals, Open Questions)
- `context/foundation/shape-notes.md` (pre-PRD discovery notes — largely duplicated into the PRD; kept as corroborating source)
- `context/foundation/roadmap.md` (vertical slices F-01, S-01..S-06 — the delivery history and stated "product wedge")
- `idea-notes.md` (raw one-page idea, Polish — earliest statement of scope)
- `README.md` (current product description + tech stack + architecture pointers)

No separate `tech-stack.md`-driven "vision doc" beyond the PRD exists; the PRD is the authoritative requirements source. All five documents agree with no material contradictions — the PRD is the most detailed and is treated as primary; `idea-notes.md` and `shape-notes.md` are cited only where they add a nuance the PRD compresses away.

**Stack / where business logic lives** (verified against `AGENTS.md` and the actual tree):
Astro 6 (`output: server`) + React 19 islands, TypeScript, Supabase (Postgres + Auth), Cloudflare Workers. Business logic is split across three layers:

- **Persistence + invariants**: `supabase/migrations/*.sql` — table shape, CHECK constraints, RLS policies.
- **Domain rules**: `src/lib/flashcards/*.ts`, `src/lib/account/schemas.ts` — validation schemas, AI-generation contract, FSRS scheduling wrapper.
- **Orchestration**: `src/pages/api/**/*.ts` — auth check → validate → call domain rule → persist, one file per operation, no service/repository layer in between.

There is no domain layer distinct from the API-route layer (no aggregates-as-classes, no repository interfaces) — the "aggregates" identified in Step 3 are conceptual groupings inferred from data ownership + invariant location, not existing code structures.

## Step 5 — Refactor ranking

Ranked by **value** (how core the invariant is to the product's stated reason for existing) crossed with **risk** (how weakly it is enforced today):

1. **#1 — "AI card requires explicit human acceptance" guardrail** (Step 3, row 3 / Step 4, row 3).
   Highest value: this is the literal "product wedge" per the roadmap's own vision recap (`roadmap.md:26-30`) and one of only two explicit Guardrails in the PRD (`prd.md:60-61`). Highest risk: it is enforced _nowhere_ server-side — purely a client-workflow assumption. Any direct API call, a client bug, or a future feature that reuses `POST /api/flashcards` can silently violate the guardrail with no server-side signal. **Recommended refactor**: make "reviewed-and-accepted" a first-class, server-verifiable fact — e.g., have `POST /api/flashcards/generate` return a short-lived, server-signed batch/generation identifier that `POST /api/flashcards` must echo back per accepted card, so acceptance is provably linked to a real prior generation rather than merely asserted by the client.

2. **#2 — 30-day retention purge dependent on external scheduling** (Step 3, row 5 / Step 4, row 4).
   High value: this is a GDPR-facing compliance guarantee stated as unconditional in the PRD (FR-010). High risk: the purge logic itself is correct and defensive (atomic claim, re-insert-on-partial-failure, non-2xx on any error, per `purge.ts:66-124`), but its _triggering_ lives entirely outside this repository (GitHub Actions cron), with no fallback path (e.g., purge-on-access) mentioned anywhere in the codebase or docs. A missed or misconfigured external cron run is invisible until someone reads Workers Logs. **Recommended refactor**: add a monitoring/alerting hook (not just a console log) or a secondary purge-on-access check, so a missed scheduled run doesn't silently exceed the promised window.

3. **#3 — Missing "Deck" as an explicit concept** (Step 4, row 1).
   Medium value / low risk today: the vision language treats "deck" as singular and implicit ("their deck"), and the current single-tenant, single-collection model satisfies every stated FR without a deck table. Not urgent, but the PRD's Non-Goals leave the door open for future multi-deck or shared-deck features (both currently out of scope, `prd.md:179`); if either is ever picked up, the lack of a `Deck` aggregate boundary today means that work starts from a schema that has no seam for it.

4. **#4 — "review" terminology collision** (Step 4, row 2).
   Lowest value/risk: purely a naming/readability issue, not a functional defect — no test or user-facing behavior is at risk. Still worth fixing cheaply: renaming `src/pages/api/flashcards/[id]/review.ts` to something like `grade.ts` (matching the `applyGrade`/`Rating` vocabulary already used in `srs.ts`) would remove the ambiguity for future contributors and AI coding agents reading the route table.

## Summary

This artifact distills 10xCards' business domain from five source documents (PRD, shape-notes, idea-notes, README, roadmap) and cross-checks every extracted term against the actual Supabase migrations, `src/lib/flashcards/*`, `src/lib/account/*`, and API routes. Ten domain terms were catalogued with source-and-code citations, two of which — **Deck** and the accept/edit/reject **Review** step — exist only as vision-level language with no corresponding persisted entity or endpoint in code. Three subdomains were classified as Core (AI generation, human-gated review, the scheduling _decision_), two as Supporting (manual authoring, card management), and two as Generic (authentication, GDPR account erasure) — notably, the FSRS _algorithm_ itself is Generic (bought, per an explicit Non-Goal) even though the _act_ of scheduling is Core to the product's value proposition. Five candidate aggregates were checked for invariant enforcement, revealing that the two hardest technical guarantees (per-row length limits, cross-user RLS isolation) are solidly enforced at the database layer, while the two most business-critical guarantees — "no AI card without explicit human acceptance" and "erase all account data within 30 days" — are enforced only weakly (client-trust and external-scheduler-dependent, respectively). The single highest-value refactor target is making AI-candidate acceptance a server-verifiable fact rather than an assumed client workflow, since it is both the product's explicitly stated differentiator and its least-enforced invariant today.
